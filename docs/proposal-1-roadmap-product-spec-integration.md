# 方案一：将产品策划案接入 Idiots Roadmap

> 状态：后续候选方案
>
> 前置条件：先完成并验证“方案二：独立的策划案驱动开发 Skill”。
>
> 目标：保留 Idiots Roadmap 的跨 Session 接力、批准门、版本保护与并行编排，同时让产品负责人只需引用或修改策划案，即可让 AI 准确定位并修复产品。

## 1. 要解决的问题

产品负责人发现体验问题时，通常能指出策划案中哪段设计不对，却不应被要求说明页面、组件、接口、状态管理或影响范围。现有 Roadmap 能安排和验收开发工作，但尚未把策划案中的具体设计单元作为日常改动入口，因此 AI 仍可能需要猜测用户指向的模块。

本方案让策划案成为产品意图入口，让 Roadmap 专注于安排工作、保护版本和跨 Session 接力。

## 2. 用户体验目标

用户只需做以下任一动作：

- 在 `产品策划案/` 中修改规则、验收条件或“待处理 / 期望”。
- 在对话里引用策划案文件或选中其中一段文字。

AI 自动完成：

1. 读取选区所属设计单元及本次文档差异。
2. 反查关联的体验、代码、测试和上下游影响。
3. 用产品语言说明“会改什么、不会改什么、是否需要取舍”。
4. 按 Roadmap 的批准门安排或执行最小修复。
5. 用策划案的验收条件验证结果，并同步实际状态与映射。

用户不需要描述模块、页面、代码位置、技术原因或影响范围。

## 3. 产品策划案规范

策划案仍保持产品经理语言。每个可以独立修改、验证或定位问题的体验单元拥有隐藏稳定 ID：

```md
<!-- ir-surface: food.manual-fallback -->
## AI 失败后的手动录入

### 用户目标
即使 AI 无法分析，用户也能完成饮食记录。

### 规则
- AI 失败后直接提供手动填写入口。
- 不丢失用户已输入的食物描述。

### 验收
- 断网或识别失败时，用户无需退出弹窗即可手填并保存。

### 当前状态
已实现待验证

### 待处理
AI 失败后现在卡在错误提示页，无法继续录入。

### 期望
保留原输入，并直接进入手动填写。
```

### 拆分规则

- 一个设计单元表达一个用户可理解的目标、规则或验收场景。
- 有独立入口、异常状态、验收方式或可独立修复的部分应拆开。
- 不为单个按钮机械建单元；只有其改变会影响独立体验或需要单独决策时才拆。
- 稳定 ID 仅供 AI 维护；标题、正文和文件结构始终以产品负责人可读为先。

## 4. Roadmap 状态扩展

在 `.idiotsroadmap/` 中新增由 AI 维护的追溯地图，例如 `product-trace.json`。它不出现在用户策划案中。

```json
{
  "surfaceId": "food.manual-fallback",
  "spec": {
    "file": "产品策划案/04-饮食记录.md",
    "heading": "AI 失败后的手动录入"
  },
  "links": {
    "upstream": ["food.ai-analysis"],
    "downstream": ["food.pending-list", "today.daily-summary"],
    "implementation": [
      {"path": "src/...", "role": "界面", "confidence": "verified"}
    ],
    "tests": [
      {"path": "tests/...", "scenario": "AI 失败后可手动保存", "confidence": "verified"}
    ]
  }
}
```

映射可信度使用 `verified`、`observed`、`inferred`、`stale`、`unknown`。低可信映射只能用来缩小排查范围，不能作为静默修改依据。

还需保存策划案快照与变更记录，以便区分：

- 用户修改策划案后的需求变更；
- 引用既有文字以报告 Bug 或要求测试；
- 文档与当前产品实际表现不一致。

## 5. Skill 家族职责调整

| 能力 | 调整后职责 |
|---|---|
| `idiots-roadmap` | 建立或接管项目时，创建产品策划案、体验单元和初始追溯地图。 |
| `idiots-roadmap-spec-change`（新增） | 日常入口：解析引用或策划案差异，定位设计单元，计算影响，形成修复批次。 |
| `idiots-roadmap-start` | 领取批准任务前，读取目标设计单元、关联地图和用户已确认的策划案规则。 |
| `idiots-roadmap-finish` | 以策划案验收条件验证；同步实际状态、测试证据和映射。 |
| `idiots-roadmap-align` | 检查“策划案承诺”与“实际前端行为”的漂移，并分类为文档过期、产品偏离或待决策。 |

## 6. 交互与批准规则

引用或修改策划案是需求定位入口，但不应绕过现有风险控制。

- 规则明确、影响边界清晰、无数据删除、权限、付费、外部接口或不兼容风险：可直接进入当前工作项的最小修复流程。
- 有多种合理的产品解释：只询问产品选择，最多给出三个产品语言选项。
- 涉及高风险内容：先展示产品影响和明确边界，等待用户批准后执行。
- 若仅引用既有文字、无文档改动、无“待处理/期望”、也无已知失败证据：AI 已定位设计单元，但必须询问希望“修复、改规则、验证还是讨论”；不能擅自改产品。

硬规则：

> 当引用位置和策划案差异足以表达需求时，AI 必须反查实现、测试和上下游体验；不得要求用户补充模块、页面、代码位置或技术影响范围。

## 7. 分阶段并入路径

### 阶段 A：验证方案二

先在一个真实项目中验证独立 Skill 是否能稳定完成“引用策划案 → 定位 → 修复 → 同步”的闭环。重点观察定位准确率、文档维护负担与用户是否真的不需要补充上下文。

### 阶段 B：提取稳定协议

确认方案二中的：设计单元格式、ID 规则、追溯地图 schema、可信度规则、策划案差异分类和原子同步方式。

### 阶段 C：接入 Roadmap

将稳定协议并入 V3 状态和现有 Start / Finish / Align 工作流；为行为变更补充 `node:test`，保持旧 Roadmap 可读。

### 阶段 D：长链验证

验证多次策划案修改、跨 Session 修复、并行任务与后续整合后，ID、产品意图、代码映射和用户已确认历史都不会漂移。

## 8. 验收标准

- 用户只引用或修改策划案，即可让 AI 定位到对应设计单元。
- AI 能说明受影响的用户体验以及明确不受影响的边界，而不要求用户解释技术影响。
- 修复后，策划案、追溯地图和验证证据不会互相矛盾。
- 策划案与实际产品冲突时，AI 清楚呈现“文档承诺”和“实际表现”，由用户决定恢复产品或更新规则。
- 现有 Roadmap 的批准门、版本保护、并行约束与不自动 push 的规则保持有效。
