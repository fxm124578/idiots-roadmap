# 方案二：独立的策划案驱动开发 Skill

> 状态：优先开发，用于验证协作模式。
>
> 目标：非程序员只需编辑、引用或选中产品策划案中的内容，AI 即能定位设计意图、反查相关实现、分析影响、完成修复并同步策划案。

## 1. 一句话定义

策划案不是开发完成后的说明书，而是产品负责人直接指挥 AI 改产品的中文控制台。

## 2. 用户操作边界

用户的输入只有两部分：

1. **引用**策划案文件、章节或选中文字，负责定位。
2. **编辑**策划案，负责表达想要的产品行为。

以下是推荐写法：

```md
### 待处理
删除后用户没有反悔机会。

### 期望
删除后显示“撤销”提示，保留 10 秒。

### 状态
待实现
```

用户修改后只需引用该文件或选区。AI 应从文件差异和选区上下文理解需求，不要求用户解释对应的模块、页面、代码或影响范围。

仅选中没有改动的旧文字时，选区能确定“在哪里”，却不能确定“要做什么”。此时 AI 可先检查已知缺口、失败证据与待验收项；若仍无意图，只问“要修复、改规则、验证还是讨论？”这一类产品问题。

## 3. 人读文档结构

建议项目内使用：

```text
产品策划案/
  00-总览与索引.md
  01-...
  02-...
```

每一份 Markdown 坚持产品语言，不出现代码路径、函数名或技术日志。每个可独立定位、改变或验收的设计单元使用隐藏稳定 ID：

```md
<!-- unit: account.login.redirect -->
## 未登录访问个人中心

### 用户目标
未登录用户不会看到空白或报错，并能完成登录后返回原页面。

### 规则
未登录用户访问个人中心时，进入登录页；登录成功后回到原页面。

### 验收条件
- 直接访问个人中心不会看到空白或报错。
- 登录成功后自动返回个人中心。

### 当前状态
已实现待验证
```

### 单元粒度

- 页面、一个完成目标的功能、业务规则、关键异常恢复或验收场景都可成为单元。
- 一个单元只承诺一个用户可判断的行为。
- 单元拆分以“能否独立发现、讨论、修改、验证”为准，不按代码目录或按钮数量拆。
- ID 由 Skill 初始化或迁移时生成；产品负责人不需要手写、背诵或理解它。

## 4. AI 维护的追溯地图

Skill 在项目中维护：

```text
.product-trace/
  state.json
  index.json
  snapshots/
  changes/
```

- `index.json`：设计单元与页面、组件、服务、路由、数据、测试和相邻体验的关联。
- `snapshots/`：策划案上次同步版本，用于识别用户的实际修改。
- `changes/`：可追溯的产品变更，不写成散乱聊天记录。
- `state.json`：索引构建、验证和同步状态。

示例：

```json
{
  "units": {
    "account.login.redirect": {
      "document": {
        "file": "产品策划案/01-账户体系.md",
        "anchor": "account.login.redirect"
      },
      "implementation": [
        {"path": "src/features/auth/LoginPage.tsx", "role": "界面", "confidence": "verified"},
        {"path": "src/routes/guard.ts", "role": "访问规则", "confidence": "observed"}
      ],
      "tests": [
        {"path": "tests/e2e/login.spec.ts", "scenario": "未登录访问后登录返回", "confidence": "verified"}
      ],
      "dependsOn": ["account.session"],
      "usedBy": ["profile.home"]
    }
  }
}
```

可信度固定为：

- `verified`：运行、有效测试或明确契约已确认。
- `observed`：从代码、路由或静态引用中观察到。
- `inferred`：根据名称或语义推断。
- `stale`：曾经成立，但代码或文档已变化，需要复查。
- `unknown`：尚无证据。

`inferred`、`stale`、`unknown` 不能被当作精确实现位置而静默修改，必须先局部验证。

## 5. 核心工作流

```text
引用策划案文件或选区
  → 读取最近的稳定设计单元、父级规则和验收条件
  → 对比快照，识别本次文档修改
  → 取得并局部复查追溯地图
  → 用产品语言说明影响范围
  → 修改最小必要实现并运行相关验证
  → 原子同步策划案状态、追溯地图和验证证据
```

影响说明必须优先回答：

- 将解决什么用户问题。
- 会影响哪些相邻体验。
- 明确不会改什么。
- 是否存在需要产品负责人决定的取舍。

不要求用户阅读代码、终端输出或测试日志。

## 6. 场景规则

| 场景 | AI 的判断与行为 | 策划案更新 |
|---|---|---|
| 新项目 | 从策划案创建单元、初始实现映射与验收场景。 | 插入隐藏 ID 和初始状态。 |
| 已有项目接管 | 只读扫描策划案、前端、代码、测试和历史；建立有可信度的地图。 | 标出已实现、待验证、缺口和冲突，不把旧文档当事实。 |
| Bug 修复 | 以选中规则作为预期，以实际表现作为现状，定位最小断点。 | 原规则通常不变；更新修复状态和回归证据。 |
| 需求变更 | 比较新旧规则和验收条件，追踪直接与间接影响。 | 更新规则、验收、依赖及变更记录。 |
| 测试 | 用户引用验收条件即可要求验证。 | 写回覆盖状态和用户可体验结论。 |
| 重构 | 确保用户行为与验收条件不变。 | 只更新实现映射，不改产品规则。 |

## 7. 歧义与风险处理

- **选区跨多个单元**：用产品语言确认是否一起处理，例如“登录与个人中心是否同时调整？”。
- **一个概念有多处实现**：按页面上下文、调用路径和测试证据排序；不能确认时展示产品选项，不问代码文件。
- **策划案与产品冲突**：明确说明“策划案承诺 A，当前产品表现 B”，请用户选择恢复 A 或将规则更新为 B。
- **找不到可靠映射**：扫描候选实现，记录可信度；无法证明时不修改。
- **测试缺失或无法运行**：可完成修改，但只能标记“已修改，待验证”，不得宣称已解决。
- **高风险修改**：数据删除、权限、收费、外部 API 与不兼容行为必须先说明产品影响并等待确认。
- **同步失败**：策划案、状态和映射必须用临时文件与原子重命名同步，禁止留下半完成状态。

## 8. 最小实现范围

先实现一个面对用户的主 Skill：`策划案驱动开发`。不要一开始要求用户选择或理解多个 Skill。

```text
product-spec-driven-change/
  SKILL.md
  scripts/
    parse-spec.mjs
    build-index.mjs
    trace-impact.mjs
    sync-spec.mjs
    validate-trace.mjs
  references/
    document-conventions.md
    state-schema.md
    confidence-rules.md
```

脚本职责：

- `parse-spec.mjs`：解析 Markdown 单元、隐藏 ID、标题层级和选区上下文。
- `build-index.mjs`：首次建立和增量刷新追溯地图。
- `trace-impact.mjs`：输出设计单元的上下游影响及可信度。
- `sync-spec.mjs`：原子保存快照、状态、变更和可读状态。
- `validate-trace.mjs`：检查 ID、文件、映射和状态是否一致。

Skill 负责产品判断、交互与执行门槛；容易漂移的解析、校验和原子写入交给 Node.js 脚本。

## 9. 第一版开发顺序

1. 定义策划案格式、隐藏 ID 与 `.product-trace/` 的 schema。
2. 实现 Markdown 单元解析、文件快照和原子同步。
3. 为已有项目实现只读索引建立：先建立“策划案单元 → 候选代码 / 测试”的可信度地图。
4. 实现“引用或策划案差异 → 单元定位 → 影响卡”的工作流，先不自动修改产品。
5. 选一个真实 Bug，完成“策划案待处理 → 最小修复 → 回归验证 → 同步”的闭环。
6. 补齐新需求、测试、冲突和索引过期的测试样例。

第一版不做：跨项目共享地图、自动全仓重写策划案、自动批准高风险变更、复杂并行编排或云端同步。

## 10. 验收标准

- 用户只引用或修改策划案，即可定位到一个稳定设计单元。
- 当策划案表达清楚时，AI 不要求用户补充模块、页面、代码位置或影响范围。
- AI 的影响说明能区分“会改”“会检查”“明确不改”。
- 修复后，策划案状态、追溯地图和实际验证证据一致。
- 文档改标题、调整位置或轻微改写后，隐藏 ID 仍保持代码映射；ID 丢失时进入恢复流程，不静默猜测。
- 测试无法运行时，系统明确标记待验证，不将修改表述为已解决。
