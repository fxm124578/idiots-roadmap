# 从计划文档到项目接力

Idiots Roadmap 最早把技术计划整理成便于验收的 Roadmap。实践中，长计划需要反复维护，新会话仍得判断进度和下一步。后来把长期目标、模块职责、接口和里程碑固定下来，只展开当前批次。`IDIOTS_ROADMAP.md` 展示进度和待决定事项，`.idiotsroadmap/state.json` 保存任务、依赖、批准和验证证据。

## 一轮工作如何交接

1. **规划。** 在 Plan 中建立基线。接手已有项目时，从代码、文档、测试和 Git 核对现状，区分已验证结果、推断和冲突。保存计划与批准开工分别处理。
2. **批准与领取。** Finish 提出下一批用户结果及其边界。用户确认后，Start 在新会话中读取项目状态、领取任务，再按当时的代码和已批准目标生成执行指令。用户结果或范围变化时重新确认。
3. **验收与收尾。** 用户验收实际页面、流程或输出，每个工作项最多两项。技术结果由独立复核检查，Finish 更新状态、提出下一批，然后停止。计划与项目出现偏差时，由 Align 区分计划过期、实现偏离和需要用户决定的变化。

早期把逐步验收说明和长提示词交给用户，增加了阅读量，旧指令也会随进度过期。后来把用户结果卡和技术指令拆开。用户决定交付结果，执行会话按最新状态制定技术步骤。`v2.2.0` 把分支、Worktree、整合和验收后的本地提交接入流程。并行工作按宿主能力优先隔离，推送由用户授权。

早期落盘依赖 Codex 和 Claude Code 的 hooks。Proma Pi 的事件差异，以及宿主可能强制 Plan 只读，促使项目提供三条保存路径：由 hooks 保存、调用 Skill 随附的工具保存，或等宿主允许写入后再保存计划。宿主的写入限制优先。

## 为什么先做独立的 spec-ops

产品反馈常常只指向策划案中的一段话。设计时比较了[接入 Roadmap](proposal-1-roadmap-product-spec-integration.md)和[独立验证](proposal-2-standalone-product-spec-driven-skill.md)两条路径，先落地独立的 [`spec-ops`](../skills/spec-ops/SKILL.md)。直接接入 Roadmap 仍是候选设计。

用户引用、选中或修改 Markdown 策划案时，Skill 用稳定 ID 定位设计单元，再核对实现和影响。只选中文字时，位置已经确定，意图仍不明确才追问。规则、目标或验收条件确实改变时，进入产品修改和验证。推断出的映射先用于检查，风险或冲突未解时先说明影响。

早期曾出现策划案改了、产品行为仍旧的问题，所以同步放在实现与验证之后。`.product-trace/` 记录策划案与实现之间的映射和证据，Roadmap 状态继续负责接力与批准。尚无证据的变更标为待验证。

Git 提交 `46a9210` 记录了 Git 收尾流程，`e92ba2c` 记录了独立的 `spec-ops` 实现，`1d4067e` 增补了安装说明。

## 恢复与验证

用 Git 取回源码后，按 [package.json](../package.json) 的声明准备 Node.js 18 或更高版本。项目使用 Node.js 标准库，无需安装第三方 npm 依赖。进入项目根目录后执行以下命令核对包结构、Skill 与插件清单，并运行全量测试。

```powershell
npm.cmd run validate
npm.cmd test
```

各宿主的 Skill 安装入口见 [项目说明](../README.md)。具体项目的 Roadmap 和运行状态由使用该 Skill 的项目维护。
